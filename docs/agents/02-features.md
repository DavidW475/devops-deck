## My Day (`src/myDay/`)

| Feature | Code |
| --- | --- |
| Ranked list of what needs you: approvals, failed runs of yours, pull requests to review, assigned work items, each with quick actions | `service.ts` (`MyDayService.get`), `model.ts` (items and actions), `rank.ts` (`RULES`) |
| Defer an item: snooze, done until it changes (fingerprint), hide; restore from the "Deferred" section | `defers.ts` (`MyDayDefers`, `snoozeUntil`), `commands.ts` (`deferItem`), commands `azureDevOps.myDay.defer` / `.restore` |

| Setting `azureDevOps.myDay.importantBranches` | `service.ts` (`importantBranches` dep), rule R2 |

Pitfalls:

- **All weights live in `rank.ts`:** the `RULES` table (id, points, label) is the only place; code and tests refer to the id. Change a weight there, not in `model.ts`.
- **Approvals:** the run id is `approval.pipeline.owner.id`; `approval.pipeline.id` is the pipeline **definition**. Mixing them opens the wrong run. An approval can only be snoozed (the run waits for it), never marked done or hidden. `Approval.pipeline` is not in Learn's object definition, see [03-azure-devops-api.md](03-azure-devops-api.md).
- **Garbage collection of defers** (`MyDayDefers.prune`) runs only for sources that loaded without error. A source that failed keeps its entries, otherwise a network error would bring back everything the user had hidden.
- **Host timer:** the service polls from the extension host (`TICK` 15 s, each source when due), because the page does not run timers while hidden. The timer starts when the sidebar view is first resolved (`start()`), not at activation. It does nothing while the window is not focused or while `throttledUntil` is in the future, and it refreshes faster only while the My Day tab is open and visible (`setVisible`, driven by the `tab` rpc and view visibility). A source is never polled more often than the setting `azureDevOps.refreshInterval` (hidden view and work items use `max(5 min, setting)`). A flight that started before `invalidate()` leaves its slot stale; a `reset()` while `getMe` is pending restarts the load in the new generation. Projects, iteration paths and defer entries match case-insensitively.
- **Keys contain colons:** item keys look like `pr:<repoId>:<id>` or `run:<project>:<id>`; the page prefixes them with `md:` for its cards (`md:pr:<repoId>:<id>`), because the other tabs use plain ids as keys. Strip the `md:` prefix (and only that) before splitting; project names may hold colons or spaces, so never split the whole key blindly.
- **View badges add up:** VS Code adds the number badges of all views in a container to the container's badge. The My Day count is shown on the dashboard view and therefore also on the activity bar icon together with the watchers view.
- **Shared raw lists:** `rawReviews(project)` and `rawApprovals(project)` give the PR and Approvals tabs the lists My Day already loaded (for 30 s, never after `invalidate()`), so the same data is not requested twice. Do not mutate them.
- **Done entries:** a "done" entry is dropped once its item shows up with another fingerprint, otherwise it would come back under *Deferred* when the item is gone. `minRequiredApprovers` 0 means that every approver has to approve (rule A3 applies).
- **Not covered (MVP):** reviews requested from a team or group and approvals assigned to a group do not show up; only direct assignment is found.
- **Not built yet:** phases 2 to 5 of the concept (`docs/concepts/2026-11-01-feature-konzepte.md`, section 3).

## Pitfalls and decisions

- **Blame starts a git process:** it is the first feature that does (everything else goes through the git extension's objects). Only `makeGitRunner` in `blameGit.ts` calls `execFile`: git path from the git extension, no shell, `cwd` is the repository root, a timeout and a buffer limit. `git blame` always gets `--no-textconv` (textconv runs configured commands). Every SHA that reaches git or a REST route first passes `isFullSha` (40 hex characters); the root of a command argument has to be a repository the git extension knows. Nothing runs in an untrusted workspace (`capabilities.untrustedWorkspaces.description` says so).
- **Blame runs are shared per line:** `BlameService` joins a running `git blame` of the same line only when it was not aborted and its timeout is not shorter (a trace uses 15 s, annotations 5 s); the answer comes from the run itself, so a `reset()` in between does not turn it into "no line". Without an upstream a commit counts as unpublished when no remote branch contains it (`getBranches({ remote: true, contains })`); a trace the user asked for ignores the 15 minute cache of "no pull request".
- **Blame window n±20:** the service blames the lines `n-20..n+20`, not only `n`. With `-M`, `-L n,n` names the commit that moved a short line when the line was moved inside a block, while a window or the whole file names the commit that wrote it (verified with git 2.56 in throwaway repositories). The neighbouring lines are cached as a side effect.
- **Only the zero SHA means uncommitted:** a line is "not committed" when its SHA is 40 zeros. Never decide that from the author text (`External file (--contents)` for a dirty buffer, which is sent through `--contents -` only when the document is dirty).
- **Hover links are limited:** the Markdown of the hover is trusted only for `HOVER_COMMANDS` (`azureDevOps.pr.openOverview`, `.pr.openInBrowser`, `.wi.open`, `.blame.openCommit`), and every piece of server or file text goes through `mdEscape`. A new link in the hover needs its command in that list and a validated argument.
- **Annotations are off by default:** VS Code already shows blame in the status bar, and GitLens and `git.blame.editorDecoration.enabled` can add a second annotation. The default surfaces are the command and the link in the built-in hover; REST calls happen on click. Annotations keep a budget of 20 pull request searches per minute and ask at most once per new commit.
- **`azureDevOps.blame.openForCommit` takes untrusted arguments:** the built-in hover passes a root and a SHA. `lookupCommit` accepts only a root of a repository the git extension knows (`repoForRoot`) and a full SHA, otherwise the state is `error`.
- **Not built yet:** the fallback through the first merge commit on the ancestry path, the commit-message link provider (`provideMessageLinks`), a `globalState` cache of commit to completed pull request, and a commit diff view. Phase 0 of the concept (a live test of `pullrequestquery` against an organization with all merge types) has not been done, see [03-azure-devops-api.md](03-azure-devops-api.md#blame-commit-to-pull-request-and-work-items).
- **Sidebar rendering (`media/sidebar.js`):** the list is updated with `patchList` (keyed by `data-key`, else tag + class; matching children are morphed, others added or removed), the toolbar with `patchHtml` and one card with `renderCard` (both morph). Identical HTML is skipped, so background refreshes and pipeline polling touch only what changed and keep hover, focus, open dropdowns and running spinners. Give every new top-level list element a stable `data-key`; attach listeners by delegation on `#app` (select `change` goes through `CHANGES`), never on elements inside morphed areas; animate opened sections with `rise()` (Web Animations), not a CSS class, because a morph rewrites `class`. The tab bar is built once (`renderTabs` toggles classes and badges, the indicator is measured in `requestAnimationFrame`), search filtering runs once per frame, and CSS keyframes animate only `transform`/`opacity` (checked in `sidebarProvider.test.ts`).
- **Template resolution:** paths without alias are relative to the including file (`/` = repository root) and stay in that file's repository; `@self` is the root pipeline's repository; `@alias` looks in the declarations inherited from the including files first (root wins), then the file's own `resources.repositories`, then any YAML file in the workspace. The context travels in the `ado-template:` URI query (`TemplateContext` as JSON); `decodeContext` validates it and only accepts local roots inside a workspace folder.
- **Template sources:** Azure Repos (`type: git`) through `AdoClient` (same auth as everything else); a local clone (matched with `localAdoRepos`, else a workspace folder with the repository's name) wins while `azureDevOps.yaml.preferLocalRepositories` is on. GitHub/Bitbucket repositories are never fetched (credentials only go to Azure DevOps), only read from a local clone.
- **Local expansion** (`TemplateExpander`) follows the server's compile-time rules: parameters are bound with types and defaults (problems become warnings, not errors), whole-value expressions keep their type, booleans become `True`/`False` in text, a `- template:` item inserts the template's list of the same kind as the surrounding key (`steps`, `jobs`, `stages`, `variables`), a list item that is only an expression returning a list (`- ${{ parameters.stages }}`) inserts its items, at most 100 files and 20 levels. Unreadable templates stay in the result marked with `__unresolved` and show as error items. Sources are kept in a `WeakMap` from expanded mappings to file + line (`yamlLine` from the parser).
- **Preview panel:** the mode is remembered in `globalState` (`pipelinePreview.mode`); local previews re-render 700 ms after any YAML edit, server previews on save of the file. The page opens sources only by index into the list the panel sent.
- **Designer edits are line edits:** `templateEdits.ts` never re-serializes YAML. It plans `LineEdit`s (replace whole lines) against the current document text; `toRangeEdits` merges touching edits into non-overlapping `WorkspaceEdit` ranges, and `applyLineEdits` computes the preview with `+`/`~` marks from the unmerged edits. Only parameters the user changed are written (`pending`); a value equal to the default removes its line unless *Write defaults* is on, and an emptied `parameters:` key is removed too. Calls with an expression path, `parameters: ${{ … }}`, a flow mapping or `${{ each }}` / `${{ insert }}` / other expression keys are read-only (`callReadOnlyReason`). `${{ if }}` / `${{ elseif }}` / `${{ else }}` keys only make the parameters under them read-only; the rest of the call stays editable (new parameters go after the conditional blocks). Also read-only: scalar parameters with block values (`|`, `>`). Note that `TemplateRef.dynamicParams` is also true for if/else keys; it means "names can't be checked completely" (diagnostics), not "read-only".
- **Designer object/list parameters:** `raw` parameters (object, step/job/stage and their lists) carry their value as YAML text in `pending`: dedented, read by `passedValue` (the whole nested block through `blockEnd`) or built from the JSON default (`defaultText`). `planStructured` replaces the parameter line plus its block with `paramLines` (inline for scalars, flow collections and expressions, else nested at the file's child column) and removes it when the value equals the default (`sameStructured`). Object parameters also get a `TreeNode` form. The webview posts the tree, the panel turns it into text with `treeText` and keeps the tree (`trees`), so empty and duplicate keys stay visible and are reported (`treeIssue`) instead of collapsing in the parsed text. Pitfalls: the form round trip drops comments inside the block and orders integer-like keys first (JS objects); the YAML field keeps the text as written. Booleans and quoted `'true'` strings stay distinct (`bool` vs `text` nodes); numbers stay strings. Lines of a block scalar are scanned as blank, so `blockEnd` counts lines indented deeper than the key as part of the block (otherwise inserts land inside a `script: |`); `# …` lines inside the block are text, which `YLine.commentCol` makes visible. Block scalar headers are read by `isBlockHeader` in either order (`|2-`, `|-2`); the writer's indentation indicator is the body column minus the key column.
- **Designer task steps:** a task step is mapped onto the template edit code, never re-serialized: `asTemplateRef(step, info)` makes it a `TemplateRef` (`inputs:` as the block key, written names replaced by the input's `yamlName`, so an alias in the file finds its parameter while the edit only replaces the value and keeps the spelling), `toParameter(input)` makes the input a parameter (required without default = no default; everything else defaults to `''` = unset and carries `unsetWhenBlank`, so a blank value is never written as `opt: ''`, also with *Write defaults*; pick lists with static, non-editable options are enums; `multiline` is a control of its own). `planCallEdits(…, 'inputs')` does the rest; new lines use `yamlName`. Edits at the same line keep the order they were given in, for the preview and the written text alike (`mergeEdits`). Pitfalls: (1) a step's `end` is exclusive, a reference's inclusive (`asTemplateRef` subtracts one), and the text of a block scalar after the last input belongs to the step (`stepEnd`); (2) visibility is computed from the file's values (the text of a block scalar, not its header) with the pending ones on top (`passedInputs`), and a required input whose rule cannot be decided is not required (like the diagnostics); an input the rule hides is shown only when the file sets it (flag `hidden`, never removed) and a hidden one that is not in the file is not in `declared`, so it is never written; (3) `planMultiline` keeps the header and the key spelling of an existing block (`withValue` on the key line, own block lines instead of `paramLines`, which would dedent script text), writes `|` for new multi-line text, a plain scalar for a single line, and `|2` when the first line starts with spaces; (4) `taskVersion` only edits the `task:` line, the form then shows the inputs of the new major and lists the ones it does not know as *Unknown inputs*; (5) *Reset* on a task step discards the form's changes (a template's *Reset to defaults* has no counterpart: an unset input has no default to restore); (6) errors for task rows come from `taskDesigner.inputError` (case-insensitive, expressions are never judged), not from `valueIssue`; (7) with `azureDevOps.yaml.taskSupport` off, or no `DesignerHost.tasks`, the structure shows no task steps, `catalogMode` stays `templates` and the task messages are ignored. The panel reads the catalog (`ensure()`) once, when Tasks mode or a task form is first needed; later changes come through `onDidChange`. The page only sends task GUIDs from the list (`pickTask` needs an id and a major that exist), indexes into `findTaskSteps` (`selectTask`) and majors the catalog has for the step's task (`taskVersion`); the list items are short (`TaskListItem`, no definitions) and sent only in Tasks mode.
- **Designer state:** the panel works on the open document (closed ones are reopened) and re-renders 300 ms after any edit of it. The selection is kept by the call's raw path and nearest line. New calls go to the end of a list found by `findInsertionPoints` (default: the last one; the user picks another). The catalog reads at most 300 YAML files with a top-level `parameters:` per repository and caches remote listings 5 minutes per repository + ref (the ↻ button forces a reload); refs come from the Refs API (tags first, newest first, then branches). Validation passes the pending text to `expandOnServer(…, text)`; error lines are only linked when there are no pending changes.
- **Template diagnostics** are debounced (600 ms) and skip expression values, `${{ if }}` keys and parameters passed as one expression; auth and "not configured" errors are silent. Remote files are cached for 30 s; saving a YAML file clears the cache.
- **Task support** (`yamlTasks.ts`): only a document with a task step reads the catalog (`ensure()`), so a pipeline-free workspace makes no request. Diagnostics use `catalogFresh` (fetched within 24 h and not `stale`) for "not installed"; without catalog data only retirement issues (`taskRetirement.ts`, no catalog needed) are shown, and auth or "not configured" failures stay silent with no sign-in prompt from the background. Completion waits at most 3 s for a first load, then returns a non-inserting "Loading tasks of <org> …" item. With `ms-azure-devops.azure-pipelines` active and language `azure-pipelines` we return no task completion (duplicates); hover and diagnostics stay. Quick fixes are matched to the stored issues by code, message and position, and insert text only (new line under `inputs:`, or an `inputs:` key; indentation and line ending from the file), never re-serialize. Hover text from the server goes through `mdEscape`; `helpMarkDown` is reduced to plain text (links to their text, images dropped, 800 characters). A snippet's new lines get the current line's indentation from the editor, so the `- ` of a step is compensated. Task names are checked against a narrow character set in `taskCatalog.ts` and again in the completion label. The name completion replaces the whole value (an existing `@2` too); inside quotes, or before a trailing comment, it inserts only the name, never the multi-line `inputs:` snippet. The catalog does not retry a failed refresh on every change event (see the backoff in [03-azure-devops-api.md](03-azure-devops-api.md)).
- **Stage dependencies:** the build timeline has no dependency information. `RunViewPanel.resolveYaml` asks the pipelines preview endpoint (`previewPipeline`, `previewRun: true`) for the expanded YAML with the run's ref, commit and template parameters, then reads `stages[].dependsOn` (`parseStageDependencies`; no `dependsOn` = previous stage). Fallback: the YAML file at the run's commit. If neither works, `stageDependencies` infers edges from start and finish times. The YAML arrives after the first render and redraws the graph (`deps` message).
- **Jobs stay open:** jobs opened automatically (failed, running or once running) stay open after the run finishes, so steps and logs remain visible. Explicit user choices are kept in webview state.
- **Log completeness:** the page decides it at request time. If the step was no longer active when the log was requested, the answer is the complete log; otherwise the page asks again (only for lines after `have`).
- **Log content is untrusted:** `stripControl` keeps color codes and drops other control sequences before output reaches the terminal; the run view escapes lines.
- **Watchers baseline:** every watcher starts with a silent baseline on its first check (and after a configuration change), so old changes do not flood in. Queries look back 2 minutes further (`OVERLAP_MS`) to tolerate clock skew. Minimum interval 60 s, default 300 s.
- **Own changes:** work item and PR watchers skip changes made by the signed-in user unless `ignoreOwnChanges: false`. Pipeline watchers report own runs by default and skip them only with `ignoreOwnChanges: true`.
- **Watcher command actions:** commands outside `azureDevOps.` run only for watchers in user settings; watchers from workspace or folder settings (`watchersInWorkspaceSettings`) skip them with a warning in the output channel, because a cloned repository could otherwise run commands with text from PRs and work items. Branch and title filters use the linear `glob` matcher, not a regular expression.
- **Branch names before git:** names from webviews or PRs go through `assertBranchName` (`src/git.ts`) before `fetch`/`checkout`/`createBranch`; a leading `-` would be read as an option.
- **Watcher settings are restricted** in untrusted workspaces (`capabilities.untrustedWorkspaces` in `package.json`), together with organization, project, additional projects, tenant and queries.
- **Wiki saves** send the page ETag; a conflict (409/412) tells the user to reopen the page instead of overwriting someone else's change. Delete and rename are not supported (done in the browser).
- **Reviewed marks** are stored locally because the web UI's storage is not public API; a mark disappears when a later iteration changes the file.
- **Approvals** are answered with the project of the run (`at(project)`); an approval that is no longer pending only shows a message.
